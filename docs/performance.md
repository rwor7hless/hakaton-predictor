# Производительность и надёжность

Замеры: `python scripts/benchmark.py` (CPU, без GPU; сырые данные —
[benchmark.json](_static/benchmark.json)).

## ML-инференс (`POST /v1/predict`, HTTP-запрос целиком)

| Пакет ТС | Без объяснений p50 / p95, мс | С SHAP-объяснениями p50 / p95, мс |
|---|---|---|
| 1 | ≈ 20 / 45 | 43 / 92 |
| 13 (весь парк validate) | 21 / 47 | 70 / 136 |
| 30 | 22 / 48 | 159 / 171 |
| 100 | 29 / 79 | 255 / 264 |

Ансамбль: 5 CatBoost + GRU в ONNX Runtime; ONNX-граф совпадает с PyTorch до
`1e-4` и считает пакет из 30 ТС за ~1.7 мс.

## Конвейер backend

| Показатель | Значение |
|---|---|
| Трекер (map matching) | 23 мкс на точку, ≈ 43 000 точек/с на одном ядре |
| Приём → прогноз (от пакета, сдвинувшего часы потока, до готовых прогнозов по всему парку), p50 / p95 | 75 / 117 мс |
| Вызов ML из backend, p50 / p95 | 71 / 106 мс |
| Поток при проигрывании ×120 | ~165 пакетов/с, очередь 0 |
| Полный день (86 тыс. пакетов, 30 терминалов) на ×2000 | ~33 с, без потерь и ошибок CRC |

Ориентир ТЗ — < 1–2 с на поток ТС — выполняется с запасом более чем на порядок.

## Качество на потоке

При проигрывании дня validate: онлайн-MAE ≈ 70 с против ≈ 130 с у наивного прогноза,
100% прогнозов с упреждением 10–15 минут, 0 прогнозов задним числом.

## Надёжность

* NDTP-сервер: мусор и битый CRC не роняют соединение (ресинхронизация по
  `0x7E7E`), ошибка в обработчике логируется, соединение живёт.
* Эмулятор и replayer переподключаются сами (проверено остановкой сервера);
  replayer досылает накопленные за время обрыва точки как `NPH_SND_HISTORY`.
* Без ML-ядра backend работает в режиме `fallback` и возвращается к ансамблю
  автоматически (проверка каждые 5 с).
* Холодный старт: backend ≈ 2 с (загрузка расписания), ML ≈ 3 с (загрузка 12
  моделей CatBoost и 2 ONNX-графов); healthcheck в compose.
